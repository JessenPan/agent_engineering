07-P1 Agent 效果评估与 bad-case 闭环-Project

用一组有真实结果断言的任务串联离线评测、模拟线上采样与失败回归。

计划中← Projects · 跨子方向07 评估、可观测性与持续改进

客服 Agent 评估系统 · 架构 v0.3 ↓架构方案

项目目标

用一组有真实结果断言的任务串联离线评测、模拟线上采样与失败回归。

客服 Agent 评估系统 · 架构 v0.3

验证客服 Agent 是否把事情办对、按规则办完，并能在用户也会操作的双控制场景中稳定重复做到。系统把可验证任务、业务结果、操作合规和沟通质量分别检查，再用线上反馈持续改进。

设计方案，尚未实现或运行评估实验。v0.3 根据 τ²-Bench 原文补充双控制状态、可组合任务与模拟器审计；发布门槛和评估效果仍需用本项目数据验证。 · 更新于 2026-10-30

系统总览一次试验如何判定如何比较退货示例组件职责资料依据
场景（Task）
一个客户目标，加上初始业务状态、适用政策和明确的成功标准。
试验（Trial）
在某个场景下完整跑一次 Agent。同一场景需要多次试验，观察是否稳定。
执行轨迹（Trace）
这次试验实际发生的消息、工具调用、状态变化与终止原因。
评估器（Grader）
根据证据作出一项判定的规则、程序、模型或人工评审；一项任务可以有多个评估器。

一次试验：谁能看到什么

运行器负责初始化和路由；Agent 与客户模拟器轮流发送消息或调用各自工具，双方只看到被授权的观测，状态变化写入共享历史。历史对话用于构造场景，测试时允许出现不同但有效的对话路径。

评估运行器 · 重置会话、Agent 侧业务状态和客户侧状态，固定版本，限制轮次、时长和费用；每个动作单独记录。

客户侧工具与状态保存客户可见的设备／账户状态，并提供受约束的客户工具。
⇄客户工具／可见状态
客户模拟器依照客户事实与目标，对最新消息作出回应。
⇄客户消息／回复
被评估 Agent使用自身策略、政策、知识与工具完成客户请求。
⇄Agent 工具／业务结果
Agent 侧业务环境保存业务世界状态，并执行 Agent 可用的读写工具。

执行证据 · 关联场景编号与试验编号，保存双方消息、工具动作、私有观测、共享状态、初末状态、错误、耗时和费用。

客户目标与已知事实 → 客户模拟器仅提供客户可见的设定、对话与客户侧工具结果。客户初始状态与工具 → 客户侧工具与状态仅客户模拟器可见；返回人类可读结果，不暴露 Agent 私有观测。业务政策、知识与工具 → 被评估 Agent使用获准访问的信息；不包含隐藏标准或参考解。Agent 侧业务状态 → Agent 侧业务环境每次试验独立重置；必要时以明确的共享状态变化影响客户侧观察。隐藏验收标准与评分细则 → 业务与政策检查仅供业务／政策检查、轨迹断言与质量评估器使用。

双控制运行中，客户侧工具只返回人类可读结果并按 Agent 请求反应式执行；模拟器不读取 Agent 的私有工具结果，也不决定是否通过。需要客户执行操作时再启用客户侧状态；一般退货场景可只保留业务侧状态。 τ²-Bench

如何判定：有效、完成、合规、好用

各项结果分别保存。先区分试验有效性与评分状态，再核验状态、动作、沟通和质量；有效试验也可能因结果证据不足而待判定／未评分。

各项评估使用的证据与判定方式
检查依据什么如何处理
1. 试验是否有效实现、任务规格、初始化、模拟器行为、环境检查和完整执行记录。标记有效、无效或无法判定，并按责任保留理由。Agent 自身超时、循环或违规仍是失败。
2. 业务是否完成目标业务状态、初末状态断言和必须告知客户的信息；优先使用程序可核验断言。确认目标是否真正达成。正确拒绝或转人工，可以是场景事先定义的成功结果。
3. 动作与政策是否合规动作发生时的身份权限、必要确认、政策版本、调用顺序和 action assertions。检查先确认再执行、必需解决动作是否出现及禁止操作等硬条件；最终状态正确也可能失败。
4. 沟通事实是否完整完整历史、客户可见消息、communication／natural-language assertions 和版本化细则。检查必要事实是否传达、解释是否清晰；允许等效表达，模型质量分不能抵消任务或政策失败。
5. 模拟器是否可靠用户每轮的 guideline、instruction、tool-use、natural continuation 标签与双人复核。分别统计 critical 与 benign 错误；先排除模拟器或任务规格问题，再进入 Agent 评分。

综合通过必须满足预先定义的任务与政策硬条件。动作／历史断言用于任务证据，不要求唯一参考轨迹；模型判定仍需在独立人工标注样本上检验。 τ²-Bench · MT-Bench

如何比较：先固定标准，再比较版本

版本比较指标与适用范围
指标怎样理解必须同时报告
任务通过率满足业务目标和政策硬条件的有效试验数 ÷ 有效试验数。同时给出全部尝试、有效、无效和有效但待判定／未评分的数量；按任务类型报告，说明未决项如何进入分母，避免平均值掩盖薄弱场景。
严重违规率发生未经授权退款等预先定义严重违规的有效试验比例。违规类型、证据和人工复核结果；不能只报告平均质量分。
重复可靠性 pass^k固定条件下，同一场景独立重复 k 次全部成功的可靠性；pass@k 则是至少一次成功。每场景计划 n ≥ k 次试验，逐场景计算后汇总，注明 n、k 与估计方法。不能将总体通过率直接取 k 次方；缺失或无效试验未补齐时，不报告该场景的完整重复可靠性。
评估器误判用独立人工标注样本检查错判，重点看严重失败被误判为通过。人工标准、任务与语言范围、样本量、分歧和未知比例；一致性高不等于业务一定成功。
沟通质量按同一版细则分别比较准确性、清晰度、有用性等维度。分数分布与典型证据。成对比较时控制答案顺序并复核分歧；不把模型偏好当作业务事实。
耗时与费用分别记录用户等待时间、每次 Agent 执行成本和整次评估成本。样本量、延迟分位数、模型用量，以及模拟器和评估器费用；与质量结果关联，但不混成单一总分。
协作差距（Default − No-User）同一任务、工具、状态和版本下，双控制与 no-user 的通过率差异。同时报告两种模式、任务分层、有效性和分母；这是推理与协作的诊断线索，不是线上因果效果。
复杂度与 persona 分层按必需动作数、原子子任务数和用户 persona 分组观察可靠性。给出各组样本量、pass^k／通过率和关键失败类型，避免总体平均掩盖长程或沟通瓶颈。

重复可靠性、模拟器错误和对照差异都依赖明确抽样与计算约定。发布判断应同时看样本量与不确定性；当前没有实际数据或经过验证的数值门槛。 τ-bench · τ²-Bench

发布决策

  • 先冻结比较条件：任务生成器与版本、场景与划分、业务和客户初始状态、政策与知识、双方工具、客户模拟器、persona、评分细则和裁判版本。对基线与候选版本使用同一评估设置，重复试验并报告任务分组结果。
  • 开发集用于修复，校准集用于改进评估器，独立评测集用于比较。由同一原始案例产生的变体放在同一划分；独立样本用于开发后，记录用途变化并补充新的保留样本。
  • 按业务风险预先约定通过条件、严重违规处理与复核要求。模型或评分规则变化时，重新评估可比较样本，不能直接拼接不同标准下的分数。
  • 需要客户主动操作的任务使用双控制；可选 no-user／oracle plan 仅用于配对诊断。离线通过后仍要检查真实业务结果、用户反馈、采样覆盖与延迟反馈；线上评分变化不替代随机 A/B 实验。

版本实例：τ-bench v2.0.0 明确说明评分与 1.x 不可直接比较。τ²-Bench 进一步显示双控制、用户工具和任务复杂度会改变结果，因此比较时必须固定整个评估配置，而不只是 Agent 模型。 τ²-Bench · τ-bench v2

示例场景：客户申请退回一副耳机

这是人为构造的示例，尚未执行测试：订单 123 在五天前送达，客户因改变主意申请退货；商品状态和其他退货政策条件均已明确满足。

验收标准：Agent 核验身份、取得必要确认并创建正确的退货记录，同时准确说明后续步骤。如果政策要求收到退货后才退款，此时不应立即退款。

同一退货任务中的不同评估结论
观察到的行为评估结论原因
核验身份、取得确认，创建正确退货记录并说明后续步骤。可判任务通过；沟通质量另评。业务目标、必要信息与动作合规均有证据。
回复“退货已办理”，但业务系统中没有退货记录。业务失败。流畅的回答不能证明动作已完成。
退货记录正确，但未取得必要确认就执行；或违规提前退款。政策失败。正确的最终状态不能抵消未经授权的操作。
模拟器编造订单事实，或测试环境初始化出错。试验无效或待复核。保留证据和数量，先确定责任，不把这次试验直接算成 Agent 成功。

各架构组件的输入、输出和关键约束
组件输入输出关键约束
业务证据 ↑有权使用的客服会话、工具事件、订单等业务状态和延迟反馈；保留原始案例编号。脱敏后的来源资料、时间范围与样本分布说明。兼顾正常、边界、拒绝、转人工与失败案例；历史话术不是唯一标准答案，模拟变体必须标注。
场景审核 ↑业务证据、当时适用的政策与知识、可恢复的初始状态。经过审核的场景、来源记录、未知事实和可接受结果。先验证初始化和参考解确实可行；不把历史客服错误写成标准答案。没有依据的事实保持未知。
任务生成与可行性验证 ↑经过审核的客户目标、初始状态、业务工具与政策；原子子任务的初始化、解决动作和最终断言。版本化任务、可行性检查结果、动作数／子任务数、用户 persona 和数据划分元数据。先运行初始化与完整解决动作，再执行断言并确认未提前满足；统一工具形式、mock 环境单测，复核欠约束、过约束和非唯一解。程序化生成是可选能力，不替代人工审核。
场景与标准库 ↑经过审核的案例、批准使用的业务政策和明确记录的假设。场景编号；客户专用事实；初始状态；政策与知识版本；业务结果与动作合规断言；评分细则；开发、校准与独立评测划分。关联案例与变体按组划分；隐藏标准与参考解不发给 Agent 或模拟器。评测样本用于开发后，记录用途变化。
评估运行器 ↑评估场景与运行配置：固定 Agent、模拟器、工具、数据、政策、知识和评估器版本，并指定重复次数、轮次、时长及费用上限。相互隔离的试验、路由后的消息与工具调用、运行编号、终止原因和执行证据。每次从新的会话与业务状态开始。结束、拒绝、转人工、超时、循环与基础设施错误分别记录；结束不等于成功。重试保留原失败记录。
客户模拟器 ↑客户专用的场景设定，以及截至当前客户可见的对话内容。下一条客户消息、澄清、同意、拒绝或转人工请求。只读取客户可见的信息，使用客户侧工具获得人类可读结果，并根据 Agent 请求反应式回应；不自主规划、不提供隐藏解法，定期按用户指令、工具使用和对话连续性人工审计。
客户侧工具与状态 ↑每次试验的客户初始状态、版本化客户工具和 Agent 的可执行指令。仅客户可见的人类可读工具结果、状态变化与对话观察。与 Agent 侧状态和私有观测隔离；工具只支持按请求的反应式操作，不暴露隐藏标准或 Agent 私有结果，状态变化可追溯。
被评估 Agent ↑客户消息、批准使用的政策与知识访问方式、工具定义和执行结果。面向客户的回复、工具调用和转人工请求。固定实际待比较的 Agent 配置；不提供参考解、模拟器指令或隐藏评分标准。评估的是 Agent 整体，而不仅是单次模型回答。
Agent 侧业务环境 ↑业务初始状态、版本化 Agent 工具约定，以及 Agent 实际发起的工具调用。工具返回结果，以及创建退货、记录退款等可观察的业务状态变化。与客户侧状态隔离，必要时通过明确的共享动态结果产生影响；按工具约定执行读写和权限检查，隔离试验与副作用，不写入真实客户系统。
执行证据 ↑来自运行器、客户模拟器、被评估 Agent 和业务环境的事件，通过运行编号与案例编号关联。场景编号、试验编号、消息与工具轨迹、双方可见观测、初末状态、共享历史、版本清单、终止原因、耗时、token 与成本。成功、失败和未评分试验都保存；区分 Agent／用户私有观测与共享状态，以执行事件和真实状态支撑判定。
试验有效性 ↑任务元数据、初始化与工具检查、双控制轨迹，以及实现、任务规格、模拟器和环境错误证据。按责任归类的有效、无效或无法判定标签，并附证据和原因。实现错误、任务规格错误、模拟器错误与 Agent 失败分开记录；Agent 自身超时、循环或违规不能随意标为无效，证据不足时交人工复核。
模拟器质量审计 ↑用户指令、persona、可用客户工具、完整消息与工具轨迹，以及任务与环境检查结果。指南遵循（guideline）、任务指令（instruction）、工具使用（tool-use）、自然连续性（natural continuation）四类标签，关键／一般错误、双人标注分歧与可靠性统计。先确认实现和任务规格无误，再抽样由两名标注者复核；关键错误与可恢复错误分开，不能把模拟器错误直接计为 Agent 失败或成功。
业务与政策检查 ↑评估器专用的验收标准、适用政策、完整工具与消息轨迹，以及业务初始和最终状态。业务结果、动作合规、必要沟通以及轨迹／历史断言的独立检查项，附证据、通过／失败／未知与严重程度。能程序验证的事实优先用状态断言；按任务需要检查必需动作是否出现、历史中是否表达必要事实，并接受等效有效路径。最终状态正确不代表确认时序合规。
沟通质量评估 ↑版本化评分细则、对话及相关执行证据，以及与任务匹配的参考事实和校准示例。各项评分、支撑证据，以及存在不确定性或分歧的判定。裁判固定模型、提示词与细则版本；检查位置、长度和风格偏好。使用相关完整上下文，允许未知；质量分不能抵消任务或政策失败。
人工复核与校准 ↑试验有效性、模拟器逐轮审计、任务结果和评分细则的检查结果，以及底层轨迹和客户场景。人工审核标签、关键／一般模拟器错误、待确定案例，以及有依据的场景或评估器修订。校准样本与独立验证样本分离；记录双人分歧、错误类型和修改理由。先修复任务或模拟器问题，再判断 Agent；修改评估标准不能替代修复真正的 Agent 问题。
版本比较与发布决策 ↑逐次试验结果、有效性标签、人工复核，以及所比较版本的固定运行配置。按任务分组的基线／候选结果、全部尝试与各类分母、重复可靠性、误判、质量、耗时与费用，以及待复核事项。比较条件和发布门槛预先确定。评分标准变化需重评；部分样本不能伪装成完整基准结果，模拟提升不能直接当作线上因果改善。
对照诊断 ↑固定任务、工具、状态、政策和版本；双控制、no-user、oracle plan 的运行结果。推理、协作沟通和长程执行的差异，以及按 persona、动作数和子任务数分层的诊断。只把配对差异用于归因线索，不当作线上因果结论；no-user 与 oracle plan 是可选诊断模式，必须报告各自配置和适用范围。
失败归因与回归 ↑经过复核的失败案例，及其准确的任务、Agent、工具、模拟器和评估器版本。可复现的失败案例、有针对性的修复和回归证据；返回运行器开展下一轮比较。分别归因 Agent、场景、模拟器、环境与评估器。校准与独立评测隔离；同一问题链接全局 Bad cases 记录，修复后保留回归与上线验证证据。
线上观察与反馈 ↑真实会话与执行记录、业务结果和延迟反馈；明确的采样规则、任务类型、版本与用户分组。质量趋势、采样覆盖、待复核案例和发布后的实际结果；重要案例进入场景库。区分单次调用与完整会话、自动分数与业务结果、模拟与真实流量。线上评估可异步；效果趋势不能代替随机 A/B 因果证据。

实施计划

  1. 定义任务成功标准，收集版本化执行记录。
  2. 对模拟生产记录采样，组合规则、模型裁判和人工复核。
  3. 分类失败、复现问题，将修复验证加入离线测试。

验收标准

  • 模拟流量明确标为模拟，不当作真实生产效果。
  • HTTP 或工具调用成功不等同于任务完成。
  • 评分器、规则与 Agent 版本均可追踪。
  • 失败案例含预期、实际、证据、归因和回归验证。
  • 质量评分使用版本化 rubric，含评价维度、分档描述、严重失败条件及人工审核示例；环境结果检查单独报告。
  • 人工与模型评分分歧有复核记录，校准样本与独立评测样本分开；修改细则不能代替修复任务失败。
  • 业务最终状态与动作时的授权／确认分别验证；评分细则的高分不得抵消任务或政策硬条件失败。
  • 每个场景可独立初始化；重复试验保存全部尝试、终止原因、有效性和分母，清楚区分 pass^k 与 pass@k。
  • 基线与候选版本使用相同场景与评估配置；评分规则变化时重评，报告人工校准范围、误判和未确定事项。
  • 上线后关联真实业务结果、采样覆盖与延迟反馈，将经复核问题转为回归案例；线上趋势与 A/B 因果结论分开。
